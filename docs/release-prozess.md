# Release-Prozess: Preview und Production mit zwei Schemas

Stand: Oktober 2026. Gilt für das Repository Wamocon_FIAE (Next.js, Drizzle, Supabase, Vercel).

## 1. Kurzfassung

Production und Preview teilen sich eine Supabase-Datenbank, aber nicht das Schema.

- `public` ist Production.
- `public_preview` ist Preview, eine Strukturkopie von `public`.

Preview bekommt nie Produktionsdaten. Die Struktur wird aus `public` geklont, Inhalte entstehen über Seed, Import oder den Inhaltsabgleich. Nach Production gelangt nur durch ein veröffentlichtes Release etwas: erst die Struktur-Migration, dann der Abgleich der Ausbildungsinhalte, dann das Deployment. Ein Merge auf `master` verändert Production nie.

## 2. Ereignisse, Migration und Deployment

| Ereignis                                                                                           | Workflow           | Migration                                                          | Deployment                                             |
| -------------------------------------------------------------------------------------------------- | ------------------ | ------------------------------------------------------------------ | ------------------------------------------------------ |
| Branch angelegt und gepusht (Migrationen oder Preview-Skripte geändert, kein offener Pull Request) | Preview Migration  | `public_preview`                                                   | keines                                                 |
| Pull Request geöffnet, danach jeder Push in den Pull Request                                       | Preview Deploy     | `public_preview`                                                   | Preview                                                |
| Pull Request gemergt (Push auf `master`)                                                           | Preview Deploy     | `public_preview`                                                   | Preview, nie Production. `public` wird nicht migriert. |
| Release veröffentlicht (ohne Prerelease)                                                           | Release Production | `public` (Struktur), danach Inhaltsabgleich der Ausbildungsinhalte | Production                                             |
| Manuell: Production Deploy                                                                         | Production Deploy  | keine, nur lesende Prüfung                                         | letztes Release                                        |
| Manuell: Preview Deploy                                                                            | Preview Deploy     | optional (`run_migration`)                                         | Branch nach Wahl                                       |
| Manuell: Inhaltsabgleich                                                                           | Content Sync       | Trockenlauf (Standard) oder Anwenden                               | keines                                                 |
| Manuell: Preview zurücksetzen                                                                      | Preview Reset      | Plan (Standard) oder Neuaufbau von `public_preview`                | keines                                                 |
| Täglich 04:17 UTC                                                                                  | Database Drift     | nur lesend                                                         | keines                                                 |
| Pull Request mit Änderungen an Datenbank oder Workflows                                            | Database Checks    | keine, kein Secret, keine Datenbank                                | keines                                                 |

Die Reihenfolge im Release ist per `needs` erzwungen: `guard`, dann `migrate`, dann `content-sync`, dann `deploy`. Schlägt ein Job fehl, startet "Re-run failed jobs" an der Stelle des Fehlers. Jeder Schritt ist wiederholbar.

Zwei Begrenzungen beim Push auf einen Branch: Der Lauf startet nur, wenn sich `supabase/migrations/**` oder die Preview-Skripte geändert haben, und er wird übersprungen, sobald für den Branch ein offener Pull Request existiert (dann übernimmt der Lauf des Pull Requests, damit nichts doppelt läuft).

### Entscheidung: lokale Bausteine statt Remote-Workflow

Der Remote-Workflow hat keinen `ref`-Input, setzt bei leerem `db_schema` den Wert `public` (ein Preview-Deployment würde dann Produktionsdaten lesen) und legt mit einem persönlichen Token Vercel-Projekte und Secrets an. Deshalb liegt die Deploy-Logik als lokale Composite Action im Repository. Das Schema ist dort kein Input, sondern folgt aus dem Ziel (Preview oder Production), der Stand des Codes kommt vom Checkout des aufrufenden Jobs, die Vercel-CLI ist fest gepinnt. Composite Actions laufen im aufrufenden Job, deshalb stehen Environment-Secrets sicher zur Verfügung.

## 4. Schutz vor Schema-Verwechslung

1. Der Preview-Deploy setzt `NEXT_PUBLIC_DB_SCHEMA` und `SUPABASE_DB_SCHEMA` immer fest auf `public_preview`, Production fest auf `public`. Die Werte aus dem Vercel-Projekt werden überschrieben, `scripts/db/deploy-env.mjs` prüft das Ergebnis und bricht bei Abweichung ab.
2. Dasselbe Skript prüft die Datenbank-Rolle in `DB_CONNECTION_STRING` exakt: Preview muss als `app_preview` oder `app_preview.<Projekt-Referenz>` verbinden. Namen, die nur so beginnen (`app_preview_migrator`, `app_previewx`), werden abgelehnt. Production darf keine der Preview-Rollen nutzen. Ist die Preview-Variable in Vercel als Sensitive angelegt (empfohlen), gibt Vercel ihren Wert nie heraus, und `vercel pull` schreibt nur den Platzhalter `[SENSITIVE]`. Dann entfällt diese Prüfung im Deploy, und die Rolle prüft die App beim Start (Punkt 4). Für Production gilt das nicht, dort muss der Wert lesbar sein.
3. `next.config.ts` bricht den Build ab, wenn ein Vercel-Production-Build nicht `public` oder ein Vercel-Preview-Build nicht `public_preview` nutzt. Auch ohne `VERCEL_ENV` (lokaler Build, Docker, anderes CI) wird `public_preview` nur mit einer `DB_CONNECTION_STRING` der Rolle `app_preview` akzeptiert. Ungültige Werte brechen jeden Build ab.
4. Die App prüft beim Start der Datenbank- und Supabase-Clients auf dem Server (`assertDbConfig`), ob Rolle und Schema zusammenpassen. Das Preview-Schema ohne passende Verbindungszeichenfolge schlägt sicher fehl.
5. Die Rolle `app_preview` hat ihren `search_path` auf Rollenebene (`public_preview, extensions`) und keine Rechte auf `public`. Der rollenbasierte `search_path` ist hinter dem Pooler robuster als ein Startparameter und schlägt sicher fehl.
6. Ohne gesetzte Variablen läuft die App wie bisher auf `public`.
7. Das Deployment gibt keine Werte aus dem Vercel-Projekt aus: Nach `vercel pull` werden alle Werte (außer `NEXT_PUBLIC_*`, `VERCEL_*` und dem Schema) mit `::add-mask::` maskiert, bevor gebaut wird. Das vollständige Vercel-Protokoll wird nicht mehr ausgegeben, nur bei einem Fehler die letzten 30 Zeilen. Ausgaben der Datenbank-Skripte maskieren die Verbindungszeichenfolge und ihr Passwort.

`NEXT_PUBLIC_*` wird beim Build eingebacken. Jedes Deployment bekommt deshalb einen eigenen Build, nichts wird zwischen Preview und Production hochgestuft.

**Sicherheitsmodell der Preview-Läufe.** Unüberprüftes Branch-SQL läuft in Preview vor dem Review. Deshalb sehen Preview-Jobs kein Production-Token. Sie verbinden sich über `PREVIEW_DB_URL` als `app_preview_migrator`. Die Grenze ist diese Datenbank-Rolle, nicht das Umschreiben der Migrationen (`public.` nach `public_preview.`). Das Umschreiben und die Sperrliste bleiben als Komfort und Frühwarnung, sie sind keine Sicherheitsgrenze mehr. Die Struktur von `public` liest ein getrennter Production-Job (nur lesend, nur Struktur, keine Zeilen) und übergibt sie als Datei.

| Job                                                                                                                  | Environment             | Token                   | Zugriff                                                |
| -------------------------------------------------------------------------------------------------------------------- | ----------------------- | ----------------------- | ------------------------------------------------------ |
| Preview Migration, Preview Deploy (Migration), Preview Reset (`rebuild`), Database Drift (`preview-drift`)           | `Preview`               | kein Supabase-Token     | `PREVIEW_DB_URL` (nur `public_preview`)                |
| Preview Reset (`snapshot`), Release Production, Production Deploy, Content Sync, Database Drift (`production-drift`) | `Production` (Reviewer) | `SUPABASE_ACCESS_TOKEN` | Projekt, lesend oder migrierend wie im Job beschrieben |

Das tägliche Drift-Programm läuft nur auf der Preview-Seite (Ledger von `public_preview` gegen die Dateien auf `master`). Der Vergleich mit `public` braucht das Production-Token und damit eine Freigabe des Environments `Production`. Ein täglicher Lauf, der jeden Tag auf eine Freigabe wartet, würde ignoriert, und ein Production-Token in einem unbeaufsichtigten Zeitplan-Lauf ist genau das, was die Sicherheitsprüfung ausschließt. Deshalb ist der Production-Teil (`production-drift`) ein manueller Lauf mit Eingabe `compare_production`, zum Beispiel nach einem Release.

**Annahmen und Restrisiken.**

- Wer auf einen Branch dieses Repositories schreiben darf, kann Workflow-Dateien und Skripte ändern und läuft im Environment `Preview`. Er kann `PREVIEW_DB_URL` und `VERCEL_TOKEN` auslesen. Folge für `PREVIEW_DB_URL`: Zugriff nur auf `public_preview`. Folge für `VERCEL_TOKEN`: ein Vercel-Token reicht meist weiter als ein Projekt, am besten ein Token mit engem Geltungsbereich verwenden. Schreibrechte auf das Repository sind deshalb vertrauenswürdigen Personen vorbehalten.
- Rechte, die `PUBLIC` jedem Datenbank-Nutzer gibt (zum Beispiel `EXECUTE` auf Funktionen in `public`, `USAGE` auf dem Schema `public`), erbt auch `app_preview_migrator`. `supabase/preview-setup/04-verify.sql` listet sie auf. Eine `SECURITY DEFINER`-Funktion in `public`, die für `PUBLIC` ausführbar ist und Daten schreibt, wäre ein Weg aus `public_preview` heraus. Das ändert diese Pull Request nicht in Production, die Liste verlangt eine Entscheidung des Eigentümers.
- Die Rolle `app_preview_migrator` kann keine Fremdschlüssel auf `auth.users` anlegen. Der Strukturklon lässt sie weg, neue Migrationen mit einem solchen Schlüssel werden mit Hinweis abgelehnt (Rahmen `-- preview:skip` ... `-- preview:end`). In Preview fehlt dadurch das Löschen per Kaskade aus `auth.users`.

## 6. Einmalige menschliche Schritte

Die Workflows führen nichts davon aus. Solange Secrets und Variablen fehlen, scheitern alle Läufe sicher in der ersten Prüfung.

1. **Schema in Supabase freigeben.** Im Supabase-Dashboard unter Project Settings, Data API, "Exposed schemas" das Schema `public_preview` ergänzen. Ohne diesen Schritt kann supabase-js (`db.schema`) das Schema nicht ansprechen.

### Demo-Bootstrap

`public_preview` ist nach jedem Reset leer: keine Plattform-Organisation, kein Superadmin, kein Betrieb. Neue Profile entstehen als TRAINEE ohne Organisation, und Konten legt dort nur ein Administrator über die Nutzerverwaltung an (Abschnitt 7, "Geteilte Auth"). Ohne diesen Schritt sieht dort niemand KfBM. Die Vorlage `supabase/preview-setup/05-demo-bootstrap.sql` richtet das Minimum ein.

- **Wer:** der Eigentümer, von Hand im Supabase SQL-Editor als Rolle `postgres`. Kein Workflow führt die Datei aus.
- **Wann:** nach den Schritten 4.1 bis 4.5, sobald die Preview bis zur Katalog-Reihe migriert ist (Migrationen bis `20261024001500`), und nachdem sich jedes der drei Testkonten einmal in der Preview angemeldet hat. Nach jedem "Preview Reset" erneut.
- **Vorbereitung:** drei Testkonten als echte Auth-Konten im Supabase-Dashboard anlegen (Authentication, Users, Add user, E-Mail bestätigen): Superadmin, Ausbilder, Azubi. Jedes Konto einmal an der Preview-App anmelden, dabei entsteht das Profil. Die drei Adressen am Anfang des Skripts eintragen (`v_superadmin_email`, `v_trainer_email`, `v_trainee_email`). Solange ein Platzhalter steht, bricht das Skript ab.
- **Was es tut:** In einer Transaktion und nur in `public_preview` legt es die Plattform-Organisation (`is_platform_owner`) und den "Demo-Ausbildungsbetrieb" an (Plan PRO, 25 Azubi-Plätze, 10 Ausbilder-Plätze, aktiv). Für die drei Profile setzt es Rolle (SUPER_ADMIN, TRAINER, TRAINEE), Organisation, `is_active` und `trainer_activated`. Die FIAE-Zeile einer neuen Organisation legt der Trigger `organizations_enable_default_catalog` an, das Skript prüft sie nur. Zum Schluss zeigt eine Ergebnistabelle je Eintrag, was passiert ist.
- **Was es nicht tut:** KfBM wird weder aktiviert noch für einen Betrieb freigegeben, es entstehen keine Katalog- und keine Einschreibungszeilen. Das macht der Superadmin in der Oberfläche (Beruf aktivieren, für den Demo-Betrieb freigeben, Azubi einschreiben), es gehört zur Abnahme. Das Skript legt auch keine Profile an und liest oder ändert nichts in Auth.
- **Wiederholen:** Das Skript ist wiederholbar, ein zweiter Lauf ändert nichts, was schon stimmt. Ein Konto ohne Profil wird mit einer Meldung übersprungen ("erst einmal anmelden, dann Skript erneut ausführen"), danach das Skript einfach noch einmal starten. Ein Konto, das schon zu einer anderen Organisation gehört, wird nicht verschoben. Bei einem Fehler wurde nichts geändert, alles läuft in einer Transaktion.
- **Auth ist geteilt:** Preview und Production nutzen dieselben Auth-Nutzer (Abschnitt 7). Die Testkonten existieren deshalb auch für Production. Dort entsteht ein Profil nur, wenn sich jemand damit an Production anmeldet, und zwar als TRAINEE ohne Organisation, ohne Rechte und ohne Daten (harmlos). Empfehlung: eigene Testkonten mit Wegwerf-Passwörtern anlegen, nicht die echten Konten von Personen.
- **Geprüft:** statisch (`tests/unit/preview-setup/demo-bootstrap.test.ts`) und mit einem Probelauf gegen eine lokale Datenbank, in der `public_preview` aus der Struktur von `public` nachgebaut war (Transaktion mit Rollback, mehrere Läufe nacheinander, Fehlerfälle). Gegen die echte Preview wurde das Skript noch nicht ausgeführt, der erste Lauf dort ist der echte Test.

### Inhalt in die Preview kopieren

`public_preview` ist nach jedem Reset ohne Inhalt: keine Kurse, Enabler, Use Cases, Quizze und Lernfelder. Solange Production das Katalogmodell noch nicht hat, kopiert die Vorlage `supabase/preview-setup/06-copy-content-from-production.sql` den Ausbildungsinhalt von `public` nach `public_preview`. Der Workflow "Content Sync" kann das noch nicht: Er braucht ein veröffentlichtes Release, wartet auf die Katalog-Migrationen in `public`, und die vorläufigen Schlüssel der Allowlist sind in Production nicht eindeutig (siehe Abschnitt 7, "Inhaltsabgleich").

- **Wer:** der Eigentümer, von Hand im Supabase SQL-Editor als Rolle `postgres`. Kein Workflow führt die Datei aus.
- **Wann:** nach dem Demo-Bootstrap (die Datei braucht das Profil des Plattform-Administrators in der Preview) und nach jedem "Preview Reset" erneut. Nach dem Rollout ersetzt der Workflow "Content Sync" (Richtung `production-to-preview`) diese Vorlage, sie bricht dann bewusst ab.
- **Vorbereitung:** am Anfang des Skripts `v_owner_email` eintragen (Adresse des Plattform-Administrators in der Preview). Solange der Platzhalter steht, bricht das Skript ab.
- **Probelauf zuerst:** `v_dry_run` steht auf `true`. Das Skript führt dann alles aus und rollt es mit einer Fehlermeldung zurück, die je Tabelle die Zahlen zeigt (Quelle, Ziel vorher, einzufügen, Ziel nachher). Erst danach `v_dry_run` auf `false` setzen.
- **Was es tut:** In einer Transaktion liest es `public` und schreibt nur in `public_preview`: Kurse, Enabler, Use Cases, Dokument-Metadaten, Quizze mit Fragen und Optionen, die Verknüpfungen der Quizze und die zwölf Lernfelder (als Lernfelder des Katalogs FIAE, nach den Regeln der Migration `20261024000500`). Die Zeilen behalten ihre Ids, damit alle Verweise stimmen. Kopiert werden nur Spalten der Allowlist `supabase/content-tables.json` und die Id. Den Ersteller von Kursen und Quizzen setzt es auf den Plattform-Administrator, Organisation und Hochlader der Dokumente bleiben leer.
- **Was es nicht tut:** Es kopiert keine Nutzerdaten (keine Profile, Organisationen, Einschreibungen, Abgaben, Fortschritte, Berichte, Bewertungen, Zeugnisse, Benachrichtigungen, keine HAI-Chats und keine Embeddings) und keine Dateien aus dem Storage (die Buckets sind geteilt, die Dokumentzeilen zeigen auf dieselben Dateien). Es ändert Production nie.
- **Wiederholen:** Ein zweiter Lauf fügt nichts mehr ein (Abgleich über die Id beziehungsweise den Schlüssel). Es ist ein Seed und kein Abgleich: Eine später in Production geänderte Zeile wird nicht aktualisiert. Nach einem Reset den Lauf wiederholen.
- **Geprüft:** statisch (`tests/unit/preview-setup/content-copy.test.ts`, mit Mutationsprüfung der Schutzregeln), als Probelauf und echter Lauf gegen die Preview am 26.10.2026 (26 Kurse, 189 Enabler, 88 Use Cases, 393 Quizze, 4222 Fragen, 16903 Optionen, 502 Quizverknüpfungen, 1003 Dokumentzeilen, 12 Lernfelder, ein zweiter Probelauf fügte nichts mehr ein). Production blieb unverändert (Zählung vor und nach dem Lauf, Ledger unverändert).

### Nutzer in die Preview kopieren

Die Auth-Konten sind zwischen Production und Preview geteilt, ein Profil in `public_preview` entsteht aber erst, wenn sich die Person dort anmeldet. Die Vorlage `supabase/preview-setup/07-copy-users-from-production.sql` kopiert die vorhandenen Profile der Plattform-Organisation von Production nach `public_preview`, damit die Personen dort sofort mit ihrer Rolle und ihrer Ausbilder-Zuordnung arbeiten können.

- **Wer und wann:** der Eigentümer, von Hand im Supabase SQL-Editor als Rolle `postgres`, nach dem Demo-Bootstrap (die Datei braucht die Plattform-Organisation der Preview) und nach jedem "Preview Reset" erneut.
- **Was sie tut:** In einer Transaktion mit einem Snapshot liest sie `public.profiles` und `public.organizations` und schreibt nur `public_preview.profiles`. Kopiert werden Id (gleich der Auth-Id), Name, E-Mail-Adresse, Rolle, Aktivierung, Ausbildungsdaten und die Ausbilder-Zuordnung, die Profile kommen in die Plattform-Organisation der Preview. Eine Zuordnung auf einen nicht kopierten Ausbilder wird leer gesetzt. Ein schon vorhandenes Profil bleibt unverändert.
- **Was sie nicht tut:** Profile von Kundenorganisationen und ohne Organisation werden nicht kopiert (der Bericht zählt sie), ebenso keine Auth-Daten (kein Passwort, kein Token) und keine Daten einer Person außer der Profilzeile (keine Einschreibungen, Abgaben, Berichte). Production wird nie geändert.
- **Probelauf zuerst:** `v_dry_run` steht auf `true`, das Skript rollt dann alles mit einer Meldung zurück, die die Zahlen zeigt. Ein zweiter Lauf fügt nichts mehr ein.
- **Geprüft:** statisch (`tests/unit/preview-setup/user-copy.test.ts`, mit Mutationsprüfung), Probelauf und echter Lauf gegen die Preview am 26.10.2026 (6 Profile in Production, 5 eingefügt, das eigene Profil war schon da).

### Testdaten mit Fortschritt

Für Abnahmetests gibt es zwei Skripte: eines legt den Azubis der Preview einen Arbeitsstand an (erledigte Enabler, Quiz-Ergebnisse, Abgaben in allen Zuständen, Tätigkeitsnachweise), das andere setzt nach einem Test alles zurück. Beide arbeiten nur in `public_preview` und sind ein Probelauf, solange `--apply` fehlt. Anleitung, Umfang und Schutz: `docs/preview-testdaten.md`.

### Vercel-Region

`vercel.json` setzt `regions` auf `dub1` (Dublin). Die Funktionen liefen bisher in `iad1` (US-Ost), die Datenbank liegt in `eu-west-1` (Irland). Jede Abfrage einer API-Route überquerte den Atlantik, bei mehreren Abfragen je Anfrage summiert sich das auf spürbare Wartezeit. Dublin liegt im selben Rechenzentrumsraum wie die Datenbank. Die Einstellung ist optional und steht in einem eigenen Commit, sie lässt sich ohne Nebenwirkung zurücknehmen. Sie wirkt nur auf Deployments dieses Repositories (Production und Preview).

## 7. Einschränkungen

Bitte vor dem Einsatz lesen. Die Preview-Umgebung ist bewusst günstig gebaut und hat Grenzen.

- **Geteiltes Preview-Schema.** Alle Branches und Pull Requests migrieren dasselbe `public_preview`. Die Migration eines noch ungeprüften Branches läuft dort vor dem Review. Zwei Branches mit unvereinbaren Migrationen stören sich gegenseitig. Gegenmaßnahmen: Datenbanksperre pro Migration, Verlauf mit Prüfsumme (eine nachträglich geänderte, schon angewendete Datei bricht den Lauf ab), Warnung bei Migrationen anderer Branches, Concurrency-Gruppen, die nie abbrechen. Wenn nichts mehr hilft: Workflow "Preview Reset". Er löscht alle Preview-Daten.
- **Neuaufbau ist wiederholbar.** Der Workflow "Preview Reset" (`rebuild`) darf beliebig oft hintereinander laufen, auch auf ein schon gefülltes `public_preview`. Der Lauf löscht zuerst alles im Schema, in der Reihenfolge der Abhängigkeiten: Sichten und materialisierte Sichten, Fremdtabellen, Tabellen, Sequenzen, Funktionen, Typen. Die Art eines Objekts kommt aus `pg_class.relkind`, nie aus dem Namen. Jede Löschanweisung sagt `IF EXISTS`, und jedes Objekt wird vor dem Löschen noch einmal nach Kennung und Art nachgeschlagen, weil ein CASCADE spätere Einträge der Liste schon entfernt haben kann. Hintergrund des früheren Fehlers: Seit der Katalog-Migration sind `lernfelder`, `lernfeld_mappings` und `v_use_case_enabler_backfill_report` Sichten, früher waren es Tabellen. Beim zweiten Neuaufbau riss das Löschen der Tabelle die Sicht per CASCADE mit, danach brach das eigene Löschen der Sicht mit "view lernfelder does not exist" ab. Bleibt nach dem Löschen etwas im Schema zurück, bricht der Lauf ab und alles wird zurückgerollt (Meldung "Rebuild aborted"). Dasselbe gilt, wenn ein Objekt außerhalb von `public_preview` von einem Preview-Objekt abhängt: Es wird nichts gelöscht. Der Lauf berührt nur `public_preview` und `preview_meta`, nie `public`, `auth` oder `storage`.
  - **Was verloren geht.** Nur der Neuaufbau leert die Preview-Daten, das ist sein Zweck. Ein normaler Lauf (`apply`, bei jedem Push) behält alle Daten und führt nur offene Migrationen aus. Das Leeren und Klonen läuft in einer Transaktion: Ein Abbruch dort ändert nichts. Bricht erst eine danach angewendete Migration ab, bleibt der geklonte Stand, und ein erneuter Neuaufbau beginnt sauber von vorn.
  - **Die Einrichtungsdateien sind ebenfalls wiederholbar.** `01-preview-role.sql`, `02-preview-side.sql` und `03-shared-objects.sql` können erneut laufen, ohne etwas zu ändern. `01` vergibt EXECUTE nur noch auf die vier Auth-Hilfsfunktionen. Vorher weitete ein erneuter Lauf von `01` nach `03` die Rechte auf `has_preview_profile` auf `anon`, `service_role` und beide Preview-Rollen aus (vorgesehen ist nur `authenticated`). `03` nimmt diese Rechte zurück, falls eine frühere Fassung von `01` sie vergeben hat. Nach jedem Neuaufbau bleibt `03` von Hand auszuführen (Realtime-Mitgliedschaft).
  - **Prüfschritt.** Der Datenbanktest `tests/scripts/db/preview-rebuild-db.test.mjs` baut `public_preview` dreimal hintereinander neu auf und vergleicht den Strukturabdruck (Tabellen, Sichten, Funktionen, Richtlinien, Rechte, Verlauf, siehe Abschnitt 9). Er läuft nur lokal, nicht in der CI.
- **Geteilte Auth.** Preview und Production nutzen dieselben Supabase-Nutzer und, solange die App den Dienstschlüssel braucht, auch denselben Dienstschlüssel (`SUPABASE_SECRET_KEY` beziehungsweise `SUPABASE_SERVICE_ROLE_KEY`). Ein Preview-Nutzer ist ein echter Auth-Nutzer, sein Profil entsteht beim ersten Aufruf von `/api/auth/sync-profile` in `public_preview`. Passwörter und Sitzungen gelten für beide Anwendungen.
  - **Konten anlegen und löschen in der Preview.** Administratoren legen in der Nutzerverwaltung Konten an (`POST /api/admin/users`) und löschen sie wieder (`DELETE /api/admin/users/[userId]`). Das Konto bekommt beim Anlegen in `app_metadata` die Kennzeichnung `preview_only: true` (`src/lib/preview-account.ts`). `app_metadata` schreibt nur der Dienstschlüssel, der Nutzer kann es nicht ändern (anders als `user_metadata`). Die Profilzeile entsteht wie bisher in `public_preview`. Die Zugangsdaten stehen in der Antwort und in der Oberfläche. Eine E-Mail mit den Zugangsdaten geht in der Preview nur hinaus, wenn der Administrator es ausdrücklich verlangt (`sendEmail: true`). In Production bleibt es beim Standard (Versand, außer bei `sendEmail: false`), und die Route setzt dort kein neues Feld. Die Oberfläche zeigt in der Preview den Hinweis, dass die Konten nur für Tests sind und Production sie nicht anerkennt.
  - **Löschen im Einzelnen.** Das Preview-Profil darf immer gelöscht werden. Das Auth-Konto wird nur gelöscht, wenn der Auth-Server die Kennzeichnung meldet: Die Route fragt mit `auth.admin.getUserById` und dem Dienstschlüssel ab, nicht nach Angaben des Clients. Bei einem Konto ohne Kennzeichnung (ein echtes, mit Production geteiltes Konto) bleibt das Auth-Konto bestehen, die Antwort enthält `authAccountKept: true` mit `authAccountKeptReason: "SHARED_ACCOUNT"`. Schlägt die Abfrage fehl oder liefert sie keinen Nutzer, bleibt das Konto ebenfalls (`CHECK_FAILED`, fail closed). `DELETE_FAILED` meldet, dass ein gekennzeichnetes Konto nicht gelöscht werden konnte, `NOT_CONFIGURED`, dass die Supabase-Variablen fehlen. Außerhalb der Preview ist das Löschen unverändert.
  - **Production erkennt gekennzeichnete Konten nicht an.** Production weist ein Konto mit `preview_only` an drei Stellen ab: bei der Anmeldung im Browser (`AuthContext.signIn`, deutsche Meldung und Abmeldung), in `/api/auth/sync-profile` (403, kein Profil, auch keine Zusammenführung mit einem vorab angelegten Profil derselben Adresse) und in der Sitzungsschicht (`src/lib/auth/session.ts`, 403 für jede API-Anfrage). Die Kennzeichnung steht in der Antwort von `auth.getUser`, es braucht keine Zusatzabfrage. Der Weg für normale Konten bleibt unverändert. **Das ist Production-Code und wirkt erst mit dem nächsten Release.**
  - **Mindestmaßnahme in der App.** Ist die Bereitstellung eine Preview (`IS_PREVIEW_SCHEMA`, `src/lib/db-schema.ts`), antworten Routen, die `auth.admin.*` nutzen und die Kennzeichnung nicht selbst behandeln, mit 403 und einer klaren Meldung, bevor sie etwas ändern. Das gilt auch für `POST /api/register` (öffentliche Selbstregistrierung, seit der E-Mail-Bestätigung ein `signUp` mit dem öffentlichen Schlüssel, siehe `docs/email-bestaetigung.md`) und für `POST /api/auth/resend-confirmation`, weil beide auf das gemeinsame Konto wirken. Auch die Registrierung im Browser (`signUp` im `AuthContext`) ist in der Preview gesperrt, damit niemand ohne Administrator Konten anlegt. Passwort zurücksetzen und eigenes Passwort ändern bleiben wie sie sind und wirken auf das gemeinsame Konto, auch auf ein echtes. Der Schutz steht in `src/lib/preview-guard.ts` (`blockInPreview`) und ist mit Tests belegt.
  - **Restrisiko.**
    - **Stand vor dem Release.** Ein in der Preview angelegtes Konto liegt ab dem Anlegen in der gemeinsamen Auth. Solange Production den Code mit der Abweisung noch nicht ausliefert, behandelt Production es wie jedes andere Konto: Eine Anmeldung dort legt über `/api/auth/sync-profile` ein Profil in `public` an (TRAINEE ohne Organisation), und weil die Adresse beim Anlegen bestätigt wird (`email_confirm`), würde das Konto mit einem vorab angelegten Production-Profil derselben Adresse zusammengeführt und dessen Rolle erben. Bis zum Release dieser Änderung deshalb in der Preview nur Testadressen verwenden, die in Production nie vorkommen (keine echten Adressen von Mitarbeitenden oder Auszubildenden), und Testkonten nach dem Test wieder löschen. Nach dem Release sind alle gekennzeichneten Konten in Production gesperrt, auch die aus der Zeit davor. Die Sperre gilt auf der Ebene der App (Anmeldung, `/api/auth/sync-profile`, Sitzungsschicht, Abmeldung bei einer wiederhergestellten Sitzung). Auf der Ebene von Supabase kann sich ein gekennzeichnetes Konto weiter anmelden und Anfragen als `authenticated` stellen, wie jedes selbst registrierte Konto, ohne Profil und damit ohne Daten, die an ein Profil gebunden sind.
    - **Adresse besetzt.** Ein Konto aus der Preview belegt die E-Mail-Adresse in der gemeinsamen Auth. Wer dieselbe Adresse in Production registrieren will, scheitert, bis das Preview-Konto gelöscht ist. Umgekehrt lässt sich eine Adresse, die in Production schon ein Konto hat, in der Preview nicht anlegen (das Konto bleibt unberührt). Die Preview antwortet dann bewusst mit einem allgemeinen Text und verrät nicht, ob die Adresse schon existiert, damit niemand Production-Adressen abfragen kann. Ein Administrator der Preview kann eine Adresse besetzen, die später ein echter Nutzer braucht, und mit `sendEmail: true` an eine fremde Adresse Zugangsdaten senden. Deshalb nur Testadressen und den Versand nur an eigene Adressen verlangen. Eine Positivliste erlaubter Adressen wäre die nächste Stufe (nicht umgesetzt).
    - **Reste.** Nach "Preview Reset" ist `public_preview` leer, die gekennzeichneten Konten bleiben in `auth.users`. Über die Oberfläche lassen sie sich dann nicht mehr löschen (die Route sucht zuerst das Preview-Profil). Der Eigentümer entfernt sie im Supabase-Dashboard, erkennbar an `raw_app_meta_data` mit `preview_only`.
    - **Dienstschlüssel und neue Routen.** Der Dienstschlüssel von Production liegt weiterhin in der Preview-Umgebung, und neuer Code in einem Branch könnte `auth.admin.*` an anderer Stelle aufrufen, ohne den Schutz zu nutzen. Neue Routen mit `auth.admin.*` brauchen deshalb im Review entweder den Aufruf von `blockInPreview()` oder eine eigene, getestete Behandlung der Kennzeichnung (anlegen mit Kennzeichnung, ändern und löschen nur bei Kennzeichnung).
    - **Trigger auf `auth.users`.** Production hat heute keinen (gemessen am 23.10.2026). Käme einer dazu, der Profile anlegt, müsste er Konten mit `raw_app_meta_data->>'preview_only' = 'true'` überspringen, sonst entstünde für jedes Preview-Konto ein Production-Profil.
  - **Der robustere Weg** bleibt ein eigenes Supabase-Projekt für Preview (eigene Auth, eigener Schlüssel, eigener Speicher). Es macht die Sperre, die Rolle `app_preview`, das Schema `public_preview` und das Präfix `preview/` überflüssig, kostet aber ein zweites Projekt und einen Abgleich der Inhalte. Das Zwei-Schemas-Verfahren ist die gewählte, günstigere Lösung mit diesen bekannten Grenzen.
- **Geteilter Storage.** Die Buckets `avatar` und `content` sind geteilt. Uploads aus Preview landen unter dem Präfix `preview/`, die Richtlinien dafür (nur für Nutzer mit Profil in `public_preview`) legt `03-shared-objects.sql` an, von Hand. Dateien, die über den Inhaltsabgleich nach Production gelangen, behalten ihren Pfad unter `preview/`.
- **Clusterweite Objekte.** Rollen, Publikationen (Realtime) und Erweiterungen gibt es nur einmal. Migrationen, die sie ändern, werden für Preview abgelehnt, die Realtime-Mitgliedschaft der Preview-Tabellen setzt `03-shared-objects.sql`, von Hand.
- **Preview läuft Production voraus.** `public_preview` hat Migrationen, die `public` noch nicht hat. Das ist gewollt. Der Drift-Check meldet es nur als Hinweis.
- **Migrationen müssen rückwärtskompatibel sein.** Zwischen Migration und Deployment läuft kurz die alte App gegen das neue Schema. Erst erweitern, später aufräumen.
- **Rolle `app_preview`** umgeht Row Level Security (wie `postgres` für Production), hat aber keine Rechte auf `public`. `04-verify.sql` belegt das.
- **Der Strukturklon.** Der Abzug von `public` quotet jeden Namen (`"public"."courses"`). Das Umschreiben und die Sperrliste kennen deshalb quotierte Namen in allen Formen, auch mit Leerzeichen, Großbuchstaben und Sonderzeichen. Fremdschlüssel auf `auth.users` fehlen im Klon, der Lauf nennt sie im Protokoll ("Note: left out foreign key ..."). Policies und Funktionen, die `auth.uid()`, `auth.role()`, `auth.jwt()` oder `auth.email()` aufrufen, bleiben erhalten: Die Rolle `app_preview_migrator` darf das Schema `auth` nicht auflösen (der Projekteigentümer kann `USAGE` darauf nicht weitergeben), deshalb ruft der Klon die gleichnamigen `SECURITY DEFINER`-Hüllen im Schema `preview_support` auf (`01-preview-role.sql`). Sie liefern dieselben Werte aus den Claims der Anfrage.
- **pgvector liegt in `public`.** Der Typ `public.vector` kann nicht geklont werden (eine Datenbank hat eine Kopie der Erweiterung). Der Klon lässt `public.vector` (und weitere Objekte von Erweiterungen in `public`, der Snapshot liefert die Namen) auf `public` zeigen. Damit beide Rollen den Typ und seine Operatoren finden, steht `public` auf ihrem `search_path` (`01-preview-role.sql` setzt das nur, wenn eine Erweiterung in `public` liegt). Das öffnet keine Daten: Beide Rollen haben keine Tabellenrechte in `public`, und die Tabellen von `public_preview` stehen auf dem Pfad vorn.
- **Grenzen der Datenbank-Rolle (im lokalen Probelauf gemessen).** Auf dem lokalen Supabase-Image (Postgres 17, wie Production ohne Superuser) hat sich gezeigt: (1) In Production (lesend gemessen) hält `PUBLIC` `CREATE` auf dem Schema `public`, beide Preview-Rollen können dort Objekte anlegen. (2) `SECURITY DEFINER`-Funktionen in `public` (`get_user_org_id`, `is_platform_owner`) sind für `PUBLIC` ausführbar. (3) Jede Anmelderolle, auch eine frisch angelegte ohne Rechte, konnte `DROP EXTENSION vector CASCADE` ausführen (zurückgerollt), weil Supabase privilegierte Erweiterungen (supautils) für alle Rollen freigibt. Das würde die Spalte `embedding` in `public.hai_embeddings` entfernen. Zu (1): Die Migration `20261025000100_security_revoke_public_create.sql` nimmt `PUBLIC` das `CREATE` auf `public`. Sie wird mit dem Katalog-Umbau in Production angewendet, bis dahin gilt (1) weiter. Zu (2): Die Funktionen rechnen nur aus `auth.uid()` und bleiben bewusst offen. Zu (3): Eine Sperre in der Datenbank ist auf dieser Plattform nicht möglich. Ein Ereignis-Trigger, angelegt von `postgres`, wurde auf dem Image in der Version von Production getestet (`ddl_command_start`, `ddl_command_end` und `sql_drop`). Er feuert bei `CREATE TABLE`, aber bei `DROP EXTENSION` kommt kein Ereignis an, weil `supautils` privilegierte Erweiterungen ohne die Ereignis-Trigger eines Nicht-Superusers ausführt. Es bleiben die Sperrliste, die `drop extension` und `alter extension` im Branch-SQL ablehnt (sie sieht nicht, was zur Laufzeit zusammengesetzt wird), das Review der Migrationen, der kleine Kreis mit Zugriff auf das Secret `PREVIEW_DB_URL` und die Sicherung von Production. Im Schadensfall fehlt die Spalte `embedding` in `public.hai_embeddings`: Erweiterung und Spalte neu anlegen und den HAI-Reindex laufen lassen. Wer dieses Restrisiko nicht tragen will, nimmt ein eigenes Supabase-Projekt für Preview (siehe oben). `04-verify.sql` (Abfragen 4, 5 und 14) zeigt den Stand.
- **Inhaltsabgleich.** Siehe Abschnitt 8, die Schlüssel sind vorläufig. Gemessen am 26.10.2026 (nur lesend) waren die ersten vorläufigen Schlüssel in Production nicht eindeutig: `content_documents` hatte 50 doppelte Schlüssel (100 Zeilen), `quizzes` 2 (5 Zeilen), `questions` 18 (36 Zeilen), `options` 1 (2 Zeilen). Der Inhaltsabgleich bricht bei einem nicht eindeutigen Schlüssel absichtlich ab, auch im Release in Richtung `preview-to-production` (Ziel `public`). Es waren keine echten Dubletten: Dieselbe Datei hängt an verschiedenen Enablern, Quizze mit gleichem Titel haben verschiedene Fragen, gleiche Fragetexte stehen an verschiedenen Positionen, und eine Option steht einmal als richtig und einmal als falsch. Deshalb sind die Schlüssel in `supabase/content-tables.json` erweitert (`content_documents`: Enabler, Use Case, Kurs, Titel, Datei, Typ; `quizzes`: Titel, Typ, Anlegezeitpunkt; `questions`: Quiz und Reihenfolge; `options`: Frage, Text, richtig oder falsch). Damit ist jede Gruppe in Production eindeutig, ohne Daten zu ändern. Die Schlüssel bleiben vorläufig: Eine nachträglich geänderte Reihenfolge einer Frage zählt für den Abgleich als neue Zeile, stabile Schlüsselspalten (Code je Zeile) bleiben die saubere Lösung. **Redaktionell zu klären (Nutzerentscheidung, keine Datenänderung durch den Abgleich):** das Quiz `034b175f-…` enthält 15 Fragen doppelt (gleicher Text und gleiche Optionen an verschiedenen Positionen, vermutlich ein doppelter Import), und eine Option der Frage `a560f9ac-…` ist mit gleichem Text einmal richtig und einmal falsch markiert.

## 8. Inhaltsabgleich

`scripts/db/content-sync.mjs` gleicht ausschließlich Ausbildungsinhalt ab, gesteuert von der Allowlist `supabase/content-tables.json`.

Regeln:

- Additiv und nie zerstörend: fehlende Zeilen werden eingefügt, gelöscht wird nie etwas.
- **Ein Release fügt nur ein** (`--update never`, Standard des Skripts). Bestehende Zeilen zu ändern ist eine eigene, bewusste Entscheidung: nur der manuelle Workflow "Content Sync" mit der Eingabe `update_mode = newer` wendet die Einstellung `update` je Tabelle an (`newer`, `always` oder `never`).
- **Spalten-Allowlist.** Je Tabelle steht in `columns` die ausdrückliche Liste der kopierten Spalten. Eine Spalte, die nicht genannt ist, wird nie kopiert, auch wenn beide Schemas sie haben (zum Beispiel neue Spalten späterer Migrationen oder `is_indexed_by_hai`). Schlüssel- und Remap-Spalten müssen in der Liste stehen, geheimnisartige Spaltennamen (`password`, `token`, `secret`, `credential`) werden abgelehnt.
- **Aktivierungsstand wird nie nach Production geschrieben.** Je Tabelle nennt `withheldFromPublic` die Spalten, die den Zustand "an oder aus" tragen (`is_active`, `is_published`, `activated_at` bei Kursen, Enablern, Use Cases und Quizzen). Mit Ziel `public` werden sie weder eingefügt noch aktualisiert: Eine neue Zeile übernimmt den Standardwert der Spalte (inaktiv, nicht veröffentlicht), eine bestehende behält ihren Zustand. Das gilt für jeden Inhalt, der neu nach Production kommt, nicht nur für KfBM. Aktiviert wird in Production bewusst, für KfBM mit dem Werkzeug "Inhalte freigeben oder sperren" (`docs/kfbm-freigabe-zuweisung.md`). Mit Ziel `public_preview` (Richtung `production-to-preview`) werden die Spalten wie aufgelistet kopiert.
- **Ersteller.** Der Abgleich prüft vor dem Lauf, ob das Profil aus `CONTENT_SYNC_OWNER_EMAIL` im Ziel existiert. Eine gesetzte, aber unbekannte Adresse bricht ab (sonst würden Zeilen mit unbekanntem Ersteller samt allem darunter still übersprungen). Fehlt die Variable, warnt der Lauf deutlich und überspringt solche Zeilen weiter, die Zahl steht in der Spalte "not present in target afterwards" und muss bei einem Apply überall 0 sein.
- **Fremdschlüssel auf Nutzertabellen.** Ist eine kopierte Spalte ein Fremdschlüssel auf `profiles`, `organizations` oder ein Objekt in `auth` oder `storage` und hat keine `remap`-Regel, bricht der Abgleich ab, bevor etwas geschrieben wird.
- Der Abgleich erkennt Zeilen über konfigurierbare Schlüsselspalten (`key`). Fremdschlüssel werden über den Schlüssel der Elterntabelle übersetzt, weil die Ids der Schemas verschieden sind. Eine Zeile, deren Elter nicht übersetzt werden kann, wird übersprungen und gezählt.
- Alles oder nichts: ein Lauf in einer Transaktion unter Sperre. Ein nicht eindeutiger Schlüssel bricht ab.
- Trockenlauf ist Standard (Transaktion mit Rollback, genaue Zahlen). Mit Anwenden folgt ein zweiter Trockenlauf, der null Änderungen melden muss. Der Bericht mit den Zahlen je Tabelle steht auch im Job-Summary des Laufs, im Release also vor der Freigabe des folgenden Deployments einsehbar.
- Nie dabei: `profiles`, Abgaben, Fortschritt, Zeugnisse, Organisationen, Benachrichtigungen, `hai_embeddings` und alles, was Nutzerdaten enthält. Der Code lehnt solche Namen selbst dann ab, wenn sie in der Allowlist stünden. `profiles` und `organizations` werden nur gelesen, um Ids zu übersetzen (E-Mail beziehungsweise Slug).
- Ersteller (`created_by_id`) werden beim Einfügen gesetzt (Profil mit der E-Mail aus `CONTENT_SYNC_OWNER_EMAIL`, falls kein Profil mit gleicher E-Mail existiert) und beim Aktualisieren nie überschrieben.
- **Lauf für einen Beruf (`--catalog <CODE>`, zum Beispiel `--catalog KFBM`).** Der Lauf liest, prüft und schreibt nur Zeilen dieses Ausbildungskatalogs. Jede Tabelle der Allowlist nennt in `catalogScope`, wie eine Zeile zum Katalog gehört: die Katalogspalte selbst (`column`), der Code der Katalogzeile (`self`) oder die Elternzeilen (`parents`, verschachtelt bis zu einer Tabelle mit Katalogspalte, jeder Elternteil zählt). Der Schlüssel des Laufs kann ein anderer sein (`catalogKey`, zum Beispiel `training_catalog_id` und `code`), damit die stabilen Codes des Berufs gelten. Die Eindeutigkeitsprüfung sieht nur die Zeilen des Berufs, FIAE-Zeilen ohne Code (alle) können den Lauf deshalb nicht abbrechen. Eine Zeile des Berufs ohne Code bricht den Lauf ab, bevor etwas geschrieben wird, ebenso ein Katalog, der in einem der beiden Schemas fehlt. Tabellen ohne `catalogScope` werden im Lauf für einen Beruf mit Hinweis übersprungen (heute hat jede Tabelle der Allowlist eine Zuordnung). Auch hier gilt: nur einfügen (im Release), nie löschen, nur Spalten der Allowlist, die Sperrliste bleibt. **Ohne `--catalog` ändert sich nichts:** gleiche Schlüssel, gleiche Prüfungen, gleiches SQL (Schnappschuss-Test `tests/scripts/db/content-sync-catalog.test.mjs`).
- **Neue Spalten in der Allowlist.** `code` (Kurse, Enabler, Use Cases, Quizze), `training_component_id` (Kurse und Quizze), `training_catalog_id` (Quizze), `enabler_id` (Use Cases, übersetzt über den Schlüssel des Enablers, denn die Ids der Schemas sind verschieden), `phase` und `kind` (Komponenten), `order_index` (Optionen) und die Einstellungen des Katalogs. Der Katalog selbst wird nur eingefügt, nie aktualisiert (`update: never`, auch nicht im Modus `configured`), und `is_active` wird nicht kopiert: Der Abgleich schaltet keinen Beruf frei, ein fehlender Katalog entsteht inaktiv. `training_catalog_id` von Enablern und Use Cases leitet ein Trigger aus dem Kurs ab, die Spalte wird nicht kopiert. Spalten, die ein Schema noch nicht hat (Migrationen noch nicht angewendet), werden still ausgelassen, ein fehlendes Schlüsselfeld bricht ab.
- **Dateien im Storage behalten ihren Pfad.** Der Abgleich kopiert nur die Metadaten (`content_documents`), keine Dateien. Ein Dokument, das in der Preview hochgeladen wurde, zeigt in Production weiter auf seinen Pfad unter `preview/` im geteilten Bucket.

### FIAE-Inhalt nach Production (`scripts/db/fiae-content-promote.mjs`)

Die Zeilen der Preview tragen die Ids von Production (die Preview wurde von dort kopiert), deshalb arbeitet es über die Id.

- **Dokumente:** Eine Zeile mit derselben Id bekommt die neuen Dateidaten (Titel, Dateiname und -größe, Adresse, Pfad, Seiten, Reihenfolge, Sichtbarkeit). Eine fehlende Zeile wird eingefügt. Die Dateien liegen im geteilten Bucket schon unter `preview/`.

Kein Quiz: neu anlegen und verknüpfen (inaktiv, wie jeder neue Inhalt). Anders: die Fragen werden an Ort und Stelle ersetzt, **nur** wenn kein Azubi eine Abgabe darauf hat und kein anderer Enabler das Quiz teilt. Sonst bleibt das Quiz unverändert und steht als Konflikt im Bericht, denn das Ersetzen der Fragen würde die Antworten der Azubis löschen (Kaskade). Konflikte werden einzeln entschieden.

## 9. Migrationen schreiben

- Datei `supabase/migrations/<14 Ziffern>_<name>.sql`, Name in Kleinbuchstaben. Zwei Altdateien mit 12 Ziffern stehen in `supabase/legacy-migrations.txt`.
- Neue Migrationen müssen neuer sein als jede Migration auf `master`. Bereits vorhandene Dateien werden nie geändert, umbenannt oder gelöscht.
- Zerstörende Anweisungen (Tabelle oder Schema entfernen, `alter table ... drop <Name>` auch ohne das Wort `column`, `drop owned`, `truncate`, `delete` ohne `where`) brauchen die Zeile `-- migration:destructive-ok`. `alter table ... drop constraint` zählt nicht dazu. Die Prüfung läuft im Pull Request gegen `master` und im Release-Lauf gegen das vorherige Release (neue Dateien seit dem letzten Release).
- Jede Migration wird für `public_preview` umgeschrieben (`public.` wird zu `public_preview.`, `begin` und `commit` werden entfernt). Was sich nicht sicher umschreiben lässt (Rollen, Publikationen, Änderungen an `auth`), lehnt die Prüfung ab. Einen Abschnitt, der für Preview nicht laufen soll, rahmen die Zeilen `-- preview:skip` und `-- preview:end`.
- Katalogabfragen brauchen ein Schema, Erweiterungen `if not exists` und `with schema extensions`.

Prüfen vor dem Push:

- `npm run test:scripts` (Unit-Tests der Skripte, ohne Datenbank)
- Optional mit einem echten Strukturabzug (Datei `public-structure.sql` aus dem Snapshot des Preview Reset, nie ins Repository): `PREVIEW_REAL_DUMP=<Pfad> npm run test:scripts`. Ohne die Variable wird dieser Test übersprungen.

- Optional der Datenbanktest für den wiederholten Neuaufbau von `public_preview`. ## 10. Rollback-Hinweise

- **App.** Production Deploy deployt immer das letzte Release. Für einen Rückschritt das fehlerhafte Release auf GitHub zurückziehen oder die Markierung "Latest" auf das vorherige Release setzen und "Production Deploy" starten. Alternativ im Vercel-Dashboard auf das vorherige Deployment zurückgehen. Das ändert nur die App, nicht die Datenbank.
- **Datenbank.** Es gibt kein automatisches Zurück. Ein Fehler in einer Migration wird mit einer neuen Migration vorwärts korrigiert. Deshalb gilt: erweitern, dann umstellen, dann aufräumen. Vor riskanten Releases eine Datenbanksicherung anlegen.
- **Inhalte.** Der Abgleich löscht nichts. Ein falsch übernommener Inhalt wird in Production von Hand korrigiert, der Abgleich überschreibt ihn nur, wenn die Quelle neuer ist (`newer`).
- **Teilweise fehlgeschlagenes Release.** Ist die Migration durch und das Deployment gescheitert, "Re-run failed jobs" starten oder "Production Deploy" verwenden. Dessen lesende Prüfung stellt sicher, dass die Migrationen schon angewendet sind.
- **Preview.** Bei kaputtem Zustand "Preview Reset" (erst `plan`, dann `execute`). Das löscht alle Preview-Daten, Production bleibt unberührt. Der Neuaufbau ist wiederholbar, auch direkt nach einem Abbruch (Abschnitt 7).
